## §7.1 Duplicate tags

X can deliver the same mention twice. Deduping *claims* is the wrong layer: two deliveries of one tag are one user action. If both reach `register_claim`, one run can finish and the other go abandoned, which looks like a withheld verdict.

Stop this **before** `register_claim`, keyed on the **mention tweet ID** (the tag reply), not the parent post and not the claim hash.

- Parent post would collapse two different people tagging the same viral tweet.
- Claim hash is not known yet at webhook time, and would block a legitimate reworded check.

Proposed implementation: persist `mention_id` (SQLite on the one server is enough) with states `received | registered | completed | failed`. Unique constraint so only one worker continues. After `register_claim`, store `run_id` on that row so a restart does not register a second run. In-memory locks are not enough.

Still need X’s timeout, retry, and whether the payload has a stable event id besides tweet id. Until then, tweet id is the idempotency key.

Not the same problem as two users tagging the same parent (§7.2) or “same claim, still fresh” (README dedupe).

## §7.2 Which post ID the contract indexes

README already says rewording makes a new claim hash but not a new post ID, so re-checks share a post’s run history. That only works if contract `post_id` is the post that **contains the claim** (usually the parent), not the `@checkreceiptz` reply.

Index the tag tweet and two tags on one viral post look unrelated; “N runs, M without a verdict” no longer describes the post being checked.

Proposed split (both IDs belong in the receipt JSON):

| ID | Role |
|---|---|
| `claim_post_id` | Contract index, run history, integrity |
| `mention_id` | Webhook idempotency, which tweet to reply to |
| `claim_hash` | Dedupe and same claim across different posts |

Two people tagging the same parent with the same normalized claim: one history, one fresh verdict (README dedupe), not two jury runs.

Triage still has to pick `claim_post_id` on quote tweets and threads (quoted post vs quoter text vs ancestor). That is a triage rule, not a reason to key the contract on the mention.

## §7.3 `receipt_cid` ordering

`submit_verdict(run_id, verdict, receipt_cid)` needs the CID. The pinned JSON cannot change after that. Do not submit first and fill the receipt later. Do not add `attach_receipt` unless we both change §4.

Order:

1. Jury finishes (votes, red team, auditors, Fusion reply text).
2. Receipt builder reads *other* runs for this post from the contract.
3. Treat **this** `run_id` as the run about to get a verdict — do not count it as pending/abandoned in the JSON.
4. Pin → `receipt_cid`.
5. `jury.receiptz` calls `submit_verdict`.
6. X reply with the receipt code (no URL).

If submit fails, the pin is an orphan and the run later goes abandoned. Retrying the same `run_id` should reuse the same CID, not register a new run.

Benny owns jury and receipt builder, so this is one in-process step: `votes → build JSON → pin → submit_verdict → X reply`. The `submit_verdict` key stays on the jury account; the builder can be a library that returns `{ receipt, receipt_cid }`.

Do not put the `submit_verdict` tx hash in the pinned JSON (it does not exist yet). Explorer can show the tx from chain after the fact.

## Take on the project

Hard for two weeks, but the README already cut it to something two people can finish if scope stays tight. The contract is a registry, not the hard part. Glue is: X mention webhooks (still unverified), minutes-long multi-model jobs that must not leave false abandoned runs, Economy APIs + hash/archive, NEAR AI signatures with `stream: false`, and TDX quotes that are not verified yet.

A realistic demo: Economy specialist, `npm run check`, contract on testnet, lookup page, abandon-demo, key-scope rejection, maybe one live X tag. Politics + crypto + live webhook + “verified” TDX on every juror is the overreach line. Do not pull Shade Agents, treasury, or staked challenges back in from PROPOSAL.md.

The combination is distinctive; the pieces are not new. Grok, Community Notes AI writers, Mira, AgentOracle, Vericore exist. What is ours is commit-then-judge, abandoned runs as the operator tell, primary records over search, mixed attestation disclosed (including that Western models are gateway-only and streamed GLM lost TEE signatures), and no-URL replies because of X pricing.

Strongest part of the repo is the write-up. Weakest risk is treating LLM jurors on excerpts as accuracy rather than an inspectable process, and dragging proposal features back in during week two.
